## InvestData 数据项目验证（用户新建，弥补 V2 缺口）

用户提供了 D:/InvestData（服务在服务器 127.0.0.1:8100，与 InvestWeb 同机）。
实测后结论：**阶段0.5 的"部分通过"可升级为"通过"**。

**关键能力**：9,818,968 行日线、10,525 标的、2021-11-22 起（1212 根）、
467 个行业板块、94,941 条板块成分股关系、三复权口径、quality_status 标记。
每日 18:30 自动更新（timer enabled），另有 POST /admin/tasks/daily-update 手动触发。

**8 个行业板块实测**（必须用成分股数校验，不能只看名称）：
| 行业 | 板块 | 成分股 | 根数 | vs ETF 相关 |
|---|---|---|---|---|
| 半导体 | 881319 | 188 | 1212 | 0.982 |
| 通信设备 | 881338 | 92 | 1212 | 0.978 |
| 化工 | 881015 | 477 | 1212 | 0.936 |
| 锂电 | 881262 电池 | 99 | 1212 | 0.942 |
| 电力设备 | 881268 电网设备 | 145 | 1212 | 0.949 |
| 有色 | 881070 | 153 | 1212 | 0.986 |
| 创新药 | 880652（概念） | 280 | 930 | 0.882 |
| 工业自动化 | 881313 自动化设备 | 83 | 1212 | 0.894 |

**重要教训**：首次用"化工"搜到 881011 石油化工（仅 18 只），与化工ETF 相关仅 **0.41**、
收益方向相反（板块+42% vs ETF-38.6%）。换 881015 化工（477 只）后升到 0.936。
→ 板块/指数选型必须看成分股数量，不能靠名称匹配。

**口径差异（必须写进结论）**：日收益相关 0.88-0.99（趋势方向一致，可用于 RS/均线/斜率），
但 5 年累计收益差 2.5%-30.9%（等权 vs 市值加权、成分范围、分红处理不同）。
→ **板块指数只能算相对强弱，不能算绝对收益预期**。

**不能补的**：行业基本面（库存/开工率）、财务数据、ETF 精确持仓（只有板块→成分股，
不是 ETF→持仓）、宏观 vintage、2021 前历史。

**接入方式**：HTTP API（日常增量）+ 只读 SQLite（全市场扫描）；禁止直写其数据库。
现有 to_secid() 只认 sh/sz/bj 前缀，需新建 providers/investdata.py。
单位陷阱：volume 是股不是手、turnover_rate 是百分数、qfq 动态需按日失效。

报告：`docs/InvestData_接入验证报告.md`

## 新一轮审计：定位修正为"全市场机会发现"（用户明确）

用户重新定义目标：**全市场机会发现/评分/排名**，明确**不涉及**账户、持仓、资金、
仓位、资产配置、交易执行、个人组合管理。

这修正了之前的开发方向：现有 portfolio / allocation / journal / risk_constraints
等"组合管理"功能与最终定位冲突，应冻结而非继续投入。

**审计核心发现（均实测）**：
1. **覆盖率 2.4%**：只扫 235 只 ETF 候选（opportunity_radar_service.py:97-99 只查
   EtfUniverse.status='candidate'）。股票 5,922 只覆盖 11、行业 467 覆盖 0、概念 459 覆盖 0。
2. **四套评分并行互不统一**：regime（市场）/ asset_signals（51 标的）/
   quality_score（235 ETF）/ opportunity_score（雷达 7 条）。
   /radar 与 /opportunities 两页面都在"打分排序"，但同一标的分数不同（73 vs 52）。
3. **25% 权重空转**：equity_cn 配置 valuation 0.15 + fundamental 0.10，
   但 _valuation_feature 仅 cash 返回有效值，fundamental 代码根本不存在。
4. **算了不用的指标**：成交量/成交额、市场广度、risk 状态、570 条事件影响
   —— 全部未进入机会分。机会分只有 4 个输入，全是价格动量。
5. **动量重复计权实测**：dev20 vs ret60 = 0.521；dev20 vs ret20 = 0.807；
   ret20 vs ret60 = 0.754（249 只候选横截面）。RS 分位也是用 ret20/ret60 排序。
6. **InvestData 零接入**：grep "investdata|8100" 零命中。
7. **生产健康**：11-20 五个关键任务全 success，asset_signals 51 标的，雷达快照 545 条。

**路线图**：P0 数据打通（1 周）→ P1 全市场评分与排名（2 周）→
P2 基本面估值（需先验证数据源）→ P3 验证与 AI。

**建议的评分 v1**：O = 100×(0.40趋势+0.25RS+0.20结构+0.15量能) × 风险系数R × 置信度C，
趋势用**斜率**替代 dev20 以消除动量重复计权；跨类只比等级（A/B/C）不比原始分。

**最关键的一步**：P1 完成后必须先做"五分组未来收益检验"，
如果最高分组与最低分组无差异，说明评分无效，一切白做。

- `backend/app/services/market_sync_service.py`：同步，1.9s，幂等（二次 0 新增）
- `backend/tests/test_investdata.py`：12 个测试

**接入方式决策**：走 HTTP API，不用 SQLite。
关键证据：`daily_bars` 库里**只有 raw**（981 万行），qfq/hfq 是 API 按复权因子实时派生的。
走 SQLite 等于自己实现复权，极易算错。API 全市场约 2.3 分钟（服务器同机）够用。

**踩到的严重 bug（已修）**：`/bars/daily` 按日期**升序**返回，最初按倒序取第一页，
`days=260` 拿到的是 2021 年的数据。修复方式：先探 coverage.last，再用日期区间请求，排序取尾部。
→ 教训：外部接口的排序假设必须用"末根日期 == 最新交易日"来断言，已写进测试。

**单位核对（45 样本）**：volume=股、amount=元（股票 1.003~1.060、ETF 0.995~1.012），
turnover_rate 百分数；与本地库 600519/000858 收盘价与成交量**完全一致**。
指数/板块的 amount/volume 不可比（成分股之和 vs 点位），属正常。

**性能**：服务器同机 14.4ms/只 → 9,724 只约 2.3 分钟；本机走 SSH 隧道 70ms/只 → 约 11 分钟。
1000 只批量成功 950（50 只新股无数据），单只失败不影响整批。

**测试**：115 passed（103 原有 + 12 新增），零回归。

**状态**：未部署生产。`INVESTDATA_ENABLED` 默认 0，不开启对现有系统零影响。
