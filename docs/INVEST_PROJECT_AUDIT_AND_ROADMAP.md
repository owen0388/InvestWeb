## 〇、五个问题，先给答案

### 1. Invest 现在究竟完成到了哪一步？

**基础设施完成 80%，机会发现能力完成 15%。**

系统能稳定采集、调度、部署、出图、跑测试（103 个用例全绿，线上 15 个任务正常）。
但"发现机会"这件事，现在只做到一件事：**从 235 只 ETF 里筛出已经在涨的**。

| 能力 | 状态 |
| --- | --- |
| 数据采集与调度 | ✅ 完成 |
| ETF 准入与质量分 | ✅ 完成 |
| 单一资产的趋势判断 | ✅ 完成 |
| **全市场扫描** | ❌ **未开始**（5222 只股票 / 467 行业 / 459 概念，覆盖为 0） |
| **统一综合评分** | ❌ **不存在**（有 4 套评分并行，互不统一） |
| **分类排名** | ⚠️ 只有 ETF 一个类别内部排名 |
| **评分变化监控** | ⚠️ 只有分数差，无排名变化、无"快速上升"识别 |
| **个体研究** | ⚠️ 有单品页，但只给资产类别评分，不是"机会分" |
| 风险评价 | ⚠️ 只有波动与回撤，缺估值/财务/流动性/事件四类 |

### 2. 现有数据是否足够开始核心开发？

**InvestWeb 自身的数据不够；InvestData 的数据够了，但一行都没接。**

| 数据源 | 规模 | 是否接入 |
| --- | --- | --- |
| InvestWeb 自采 | 94,662 行 / 284 标的 / 2023-08 起 | 已在用 |
| InvestData | **9,818,968 行 / 10,525 标的 / 2021-11 起** | ❌ **零接入** |

`grep -rn "investdata\|8100" backend/app/` → **零命中**。

**结论**：接入 InvestData 后，利用行情数据就能做出第一版全市场机会评分。**不需要等基本面数据。**

### 3. 当前最应该开发的是什么？

**接入 InvestData + 建立单一综合评分 + 全市场排名。** 不是加功能，是把散落的 4 套评分收成 1 套，并把扫描范围从 235 只扩到 9,700 个标的。

### 4. 哪些工作暂时不应该做？

| 不该做 | 理由 |
| --- | --- |
| 组合配置 / 交易日志 / 持仓管理 | 与"全市场机会发现"定位冲突，已有代码存在但应**冻结** |
| 行业基本面（库存/开工率/订单） | 无稳定数据源，且第一版评分不依赖它 |
| ETF 精确成分穿透 | InvestData 只有"板块→成分股"，没有 PCF 申赎清单 |
| 更多 AI 分析 | 当前 `LLM_ENABLED=0`，一次都没跑过，先证明规则评分的价值 |
| 分钟线 / 实时行情 | 与日频机会发现无关，成本高 |

### 5. 下一步最优开发顺序？

### 2.1 功能重复与割裂（重要）

**重复 1：两套"打分排序"页面**

| 页面 | 接口 | 数据源 | 覆盖 | 口径 |
| --- | --- | --- | ---: | --- |
| `/radar` 机会雷达 | `/api/opportunity-radar/daily` | 实时计算 | 235 只 ETF | 机会分 = 趋势60% + RS40% |
| `/opportunities` 资产评分 | `/api/opportunities` | `asset_signals` 表 | 51 只 | 综合分 = 6 特征加权 − 风险惩罚 |

**同一个"给标的打分"的诉求，系统给两个页面、两套分数、两套动作词。**
用户在 `/radar` 看到"积极研究 73 分"，在 `/opportunities` 看到同一只标的是"维持配置 52 分"——**无法解释**。

**重复 2：两套风险表达**

- `regime` 给市场一个 0–100 分 + 4 个状态
- `asset_signals.risk` 给单资产一个风险分
- 雷达卡片里没有任何风险分，只有文案
- 三者不联动

**割裂 1：事件与机会完全不相通**

事件有 137 个、570 条影响关系，但**没有任何一个事件进入机会分**。
`radar_card` 里写的是"本卡基于价量，未关联具体新闻事件"——诚实，但也说明事件模块与决策链断开。

**割裂 2：市场风险状态不进机会分**

`regime` 算出"风险偏好下降 29.5"，但机会雷达的筛选与打分**完全不看这个值**。
在熊市里它照样会给出 10 条"积极研究"。

## 六、当前机会发现能力

### 6.1 扫描范围（核心问题）

```python
# opportunity_radar_service.py:97-99
candidates = db.scalars(
    select(EtfUniverse).where(EtfUniverse.status == "candidate")
).all()
```

**扫描范围 = 235 只 ETF 候选。仅此。**

| 对象 | 市场实际数量 | Invest 覆盖 | 覆盖率 |
| --- | ---: | ---: | ---: |
| A 股股票 | 5,922 | 11（在 instrument_master） | **0.2%** |
| ETF | 2,876 | 235 | 8.2% |
| 行业板块 | 467 | 0 | **0%** |
| 概念板块 | 459 | 0 | **0%** |
| 指数 | 801 | 12 | 1.5% |

**结论：这不叫全市场扫描，叫"ETF 候选池筛选"。**

三个结构性限制：

1. **依赖固定候选名单**：候选池来自 `etf_universe` 表，由 `universe_refresh` 每日维护。新 ETF 要等它刷新才可能进来。**无法自动发现名单外的新机会。**
2. **完全不看股票**：5,922 只股票被排除在外。
3. **完全不看行业/概念**：无法回答"哪个行业在改善"。

### 6.2 指标及其实际作用

| 指标 | 是否计算 | 是否进入最终分数 | 证据 |
| --- | --- | --- | --- |
| 价格 / MA20 / MA60 | ✅ | ✅ 通过 `ma_order`、`dev20` | `trend_features` |
| 20/60 日收益 | ✅ | ✅ `ret60` 进趋势分 | 同上 |
| 波动率 vol20 | ✅ | ✅ 超阈值降级（`max_vol`） | `decide_state` |
| 250 日回撤 | ✅ | ✅ 超阈值退出 | 同上 |
| 相对强弱分位 | ✅ | ✅ 占机会分 40% | `relative_strength_scores` |
| 成交量 / 成交额 | ✅ 采集 | ❌ **只在质量分里用作流动性** | 未进机会分 |
| 市场广度 | ✅ 6 个宽基 | ❌ 只在 regime 里 | 未进机会分 |
| 市场风险状态 | ✅ | ❌ **完全没有联动** | — |
| 事件影响 | ✅ 570 条 | ❌ **完全没有联动** | — |
| 估值 | ❌ 仅 cash | ❌ | `_valuation_feature` 返回 None |
| 财务基本面 | ❌ | ❌ | 代码中不存在 |

**关键判断**：
- **真正进入机会分的只有 4 个量**：均线关系、dev20、ret60、RS 分位
- 成交量、广度、风险状态、事件**全部是"算了但没用"**
- 这正是"把所有指标做成仪表盘，让用户自行判断"的典型

### 6.3 指标重复性

`trend_strength = 35×(ma20>ma60) + 35×min(dev20/20%,1) + 30×min(ret60/30%,1)`

- `dev20` 与 `ret60` 都是价格动量，**高度相关**
- 路线图 6.4 明确要求"避免同一类价格动量信号重复计权"
- 现状：**三项全是动量，实际是"动量平权打分"**

### 7.2 权重与算法（实测）

**regime**（`signal_rules.yaml:regime.components`）

```
权益趋势 0.30 | 权益动量 0.20 | 波动率 0.20 | 广度 0.15 | 避险 0.10 | 事件 0.05
阈值：risk_on≥62, risk_off≤38, 覆盖率<0.45 不出分
```

**asset_signals**（`scoring.modules.equity_cn`）

```
trend 0.30 | valuation 0.15 | fundamental 0.10 | macro 0.15 | catalyst 0.20 | liquidity 0.10
total = Σ(w×value)/Σ(存在w) − 0.5×max(0,55−risk_value)×0.35
动作阈值：72/62/45/35/25
```

**quality**（`quality_service.DEFAULT_WEIGHTS`）

```
流动性 0.40 | 规模 0.30 | 折溢价 0.20 | 历史 0.10
全池 rank 归一，覆盖率<0.5 的维度禁用
```

**opportunity**

```
趋势强度 = 35(多头) + 35×dev20/20% + 30×ret60/30%
机会分 = 趋势×0.6 + RS×0.4
```

### 7.3 问题清单

| # | 问题 | 严重度 | 证据 |
| ---: | --- | --- | --- |
| 1 | **四套评分互不引用**，同一标的不同页面分数不同 | 🔴 高 | `/radar` 73 分 vs `/opportunities` 52 分 |
| 2 | **25% 权重空转**：valuation+fundamental 占 0.25，实际只有 cash 有估值 | 🔴 高 | `_valuation_feature` 返回 None |
| 3 | **机会分 100% 由动量驱动**，无基本面、无风险、无事件 | 🔴 高 | 三项加项全是涨幅 |
| 4 | **风险状态不参与机会筛选**，熊市照出"积极研究" | 🔴 高 | `radar` 不读 `regime` |
| 5 | 动量因子重复计权（dev20 与 ret60 相关） | 🟡 中 | 路线图 6.4 明确禁止 |
| 6 | 无跨类别可比性（股票/ETF/行业用同一套阈值） | 🟡 中 | 只有 ETF 有分 |
| 7 | 不可解释"为什么涨得好但分下降" | 🟡 中 | 无因子贡献分解，只有总分 |
| 8 | 无评分版本管理 | 🟢 低 | 有 `version` 字段但恒为 1 |

### 7.4 是否存在"某指标过度主导"

**是。** 趋势强度 60% + RS 40%，两者都是动量。

**实测相关系数**（249 只候选横截面）：

```
dev20 vs ret60 = 0.521    ← trend_strength 实际使用的两个因子
dev20 vs ret20 = 0.807
ret20 vs ret60 = 0.754    ← 短期与中期动量高度重叠
```

`trend_strength` 用的 `dev20` 与 `ret60` 相关 0.521，属中等偏高；但若把 `ma_order`（同为趋势方向）一并计入，三项**共享同一信息源**。
再加 RS 分位也是用 `ret20×0.5 + ret60×0.5` 排序——**四个输入全部是价格动量**。

这解释了为什么酒 ETF（距 MA20 +7.4%）能拿 73 分：**它只是涨得猛，不代表机会好**。

## 十一、当前最关键的能力缺口

按重要性排序：

### 缺口 1：扫描范围（🔴 致命）

235 只 ETF vs 9,700 个可投资对象。**覆盖率 2.4%**。

不做这个，"全市场机会发现"这个定位就是空的。

### 缺口 2：统一评分（🔴 致命）

4 套评分 = 4 个答案。用户问"哪个机会最好"，系统给不出唯一答案。

### 缺口 3：跨类别可比（🟡 重要）

股票、ETF、行业不能直接比原始指标。需要：
- 类别内 z-score / rank 归一
- 输出"类别内排名" + "跨类等级（A/B/C）"

### 缺口 4：变化监控（🟡 重要）

现在只有"今天分数"，没有：
- 排名变化（从第 50 升到第 8）
- 分数变化速度
- 新进入高分区
- 风险快速恶化

**"机会变化"比"机会快照"更有价值**——但系统完全没有。

### 缺口 5：个体研究（🟡 重要）

`/assets/:symbol` 有单品页，但给的是"资产类别综合分"，不是"这只能不能买、为什么"。

用户要求的能力（综合评分/排名/趋势/RS/风险/优势/风险/依据/历史变化）**大部分没有**。

## 十三、建议的综合机会评分体系

### 13.1 设计原则

1. **一个总分 + 四个分项**，不再有第二套分数
2. **类别内标准化**，跨类只比等级
3. **风险独立成项且可扣分**，不藏在状态里
4. **每个分数可拆解到因子贡献**
5. **缺失数据降置信度，不补中性分**

### 13.2 评分结构（v1，仅用行情数据）

```
机会总分 O = 100 × ( 0.40×趋势 + 0.25×相对强度 + 0.20×结构 + 0.15×量能 )
             × 风险系数 R          （0.6 ~ 1.0，风险越高系数越低）
             × 置信度 C            （0.5 ~ 1.0，数据越缺越低）
```

| 分项 | 权重 | 构成 | 数据 |
| --- | ---: | --- | --- |
| **趋势** | 0.40 | MA20/60/120 排列 + 斜率 + 偏离（**去重**：用斜率替代重复的 dev20） | 行情 |
| **相对强度** | 0.25 | 相对基准的 20/60/120 日比值 + 横截面排名 | 行情 |
| **结构** | 0.20 | 低点抬高、区间收敛、距前低、突破守住 | 行情 |
| **量能** | 0.15 | 上涨/下跌量比、突破量比、回调缩量 | 行情 |

**风险系数 R**：

```
R = 1 − 0.15×波动惩罚 − 0.15×回撤惩罚 − 0.10×流动性惩罚
（仅对 ETF 用流动性；股票用成交额分位）
```

**置信度 C**：

```
C = 0.5 + 0.5 × (可用因子权重 / 总权重) × 数据质量
数据不足 250 根 → C ≤ 0.7
```

### 13.3 为什么这样设计

| 设计 | 解决什么 |
| --- | --- |
| 趋势用**斜率**不用 dev20 | 消除动量重复计权 |
| 结构单独成项 | 识别"底部区间"，而不是等突破 |
| 风险独立成乘法系数 | 高风险直接压低总分，而不是只降级状态 |
| 置信度独立 | 数据不全时不假装有把握 |
| 四项都在 0–100 | 可分项展示"为什么是这个分" |

### 13.4 跨类别处理

| 层级 | 做法 |
| --- | --- |
| 类别内 | 原始因子 → 类别内 z-score → 0–100 |
| 类别间 | 只比较**等级**：A(前10%) / B(前30%) / C(其余) |
| 展示 | "半导体 881319：行业类第 3/467，等级 A" |

**不承诺"股票 85 分 > 行业 80 分"这种跨类可比**，只给等级。

## 十四、全市场机会排名的实现思路

### 14.1 扫描对象与规模

| 类别 | 数量 | 每日计算量（1212 根 × 指标） |

| ETF | 2,876 | 同上 |
| 行业 | 467 | 轻 |

**性能估算**：现有 235 只用 pandas 逐只算约 3 秒 → 9,724 只约 2 分钟。可接受（每日一次）。

若优化为向量化（一次算全市场矩阵），可降到 20–30 秒。

### 14.2 数据流

```
InvestData（1212 根 × 9,724 标的）
    ↓ 只读 SQLite 批量读取（比 HTTP 快 100 倍）
技术指标批算（向量化）
    ↓
类别内 z-score 归一
    ↓
机会总分 O = f(趋势, RS, 结构, 量能) × R × C
    ↓
分类排名（stock/etf/industry/concept 各自 rank）
    ↓
写入机会快照表（含 model_version）
    ↓
API：排名 / 详情 / 变化 / 个体研究
```

### 14.3 每日产出

| 产出 | 内容 |
| --- | --- |
| 全市场排名 | 4 个类别各 Top 100 |
| 新进入高分区 | 首次进入前 10% 的标的 |
| 快速上升 | 排名 5 日提升 > 20 位 |
| 风险恶化 | 风险系数 5 日下降 > 15% |
| 分数下降但涨幅为正 | 解释：因子贡献变化 |

| 能力 | 现状 | 需要做什么 |
| --- | --- | --- |
| 前视偏差（价格） | ✅ 已防 | — |

**最该先做的验证**：

```
把过去 3 年每日的机会分算出来
→ 按分数分 5 组
→ 看第 1 组（最高分）未来 20 日收益 vs 第 5 组
→ 如果两组没差异，说明评分无效，一切白做
```

这是验证"评分体系是否成立"的唯一硬标准，**应该在开发评分前就先跑通**。
